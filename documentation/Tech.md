# Virasat Setu Comprehensive Technical Specification:

This document provides complete technical specifications for the Virasat Setu platform, covering the framework components, database architecture, API endpoint reference, security models and algorithmic definitions.

Technology Stack Architecture:
1. Backend Application: FastAPI (Asynchronous Python).
2. ASGI Server Engine: Uvicorn (High Concurrency).
3. Data Access Layer: SQLAlchemy ORM (Declarative Models).
4. Data Validation: Pydantic v2 (Strict Type Safety).
5. Primary Cloud Database: Supabase (PostgreSQL with RLS).
6. Local Embedded Database: SQLite (Zero Setup Storage).
7. Security Infrastructure: PyJWT and Passlib (Bcrypt and JWT).
8. Frontend Presentation: Tailwind CSS (Responsive Semantic).
9. Serverless Hosting: Vercel (Unified Gateway).


## Detailed Database Schema Definitions:

The platform data store comprises eleven relational tables linked via UUID primary keys and foreign key constraints:

### 1. Users Table:

Stores authentication credentials, user profiles and assigned access roles.

1. id: String UUID primary key uniquely identifying the user.
2. email: String unique email address used for sign in and official alerts.
3. hashed password: String containing cryptographic bcrypt password hash.
4. full name: String storing the citizen or official legal name.
5. role: String designating authorization tier (family user, admin, institution rep).
6. mobile: String storing registered contact number.
7. institution id: Optional foreign key linking institutional representatives to their organization.
8. created at: Timestamp recording account creation.


### 2. Institutions Table:

Maintains directory of participating banks, life insurance companies and mutual fund houses.

1. id: String UUID primary key.
2. name: Full legal name of the financial institution.
3. institution type: Category identifier (bank, insurance, mutual fund).
4. contact email: Official nodal email address.
5. helpline: Official customer support telephone line.
6. website url: Official institutional portal address.
7. created at: Timestamp of institutional onboarding.


### 3. Deceased Persons Table:

Stores civil records of deceased family members submitted for asset discovery.

1. id: String UUID primary key.
2. user id: Foreign key linking record to the submitting family user.
3. full name: Full legal name of the deceased individual.
4. date of birth: String in ISO format YYYY MM DD.
5. date of death: String in ISO format YYYY MM DD.
6. gender: Gender classification.
7. last known city: Last known municipal jurisdiction.
8. last known state: Last known federal state or territory.
9. death cert ref: Municipal death registration reference code.
10. sample identity ref: Permanent Account Number or national identity reference.
11. death reg date: Official date of civil death registration.
12. issuing authority: Municipal entity that issued the certificate.
13. status: Verification state (Pending Verification, Verified, Rejected).
14. admin notes: Optional administrative review remarks.
15. created at: Submission timestamp.


### 4. Financial Assets Table:

Indexed repository of dormant accounts, mature policies and unclaimed investment folios.

1. id: String UUID primary key.
2. institution id: Foreign key linking asset to holding institution.
3. asset type: Asset category (bank, insurance, mutual fund).
4. institution name: Denormalized institution title for fast queries.
5. holder name: Registered owner name on institutional file.
6. date of birth: Registered birth date on file.
7. sample identity ref: Identity reference on institutional record.
8. account ref: Masked account number, policy number or folio code.
9. category: Specific product type (Savings, Fixed Deposit, Endowment, Equity Fund).
10. nominee ref: Registered nominee name on file.
11. status: Current status flag (Unclaimed, Active, Inactive).
12. unclaimed status: Dormancy classification (Dormant Over 10 Years, Mature Unclaimed).
13. approximate value: Estimated asset valuation in Indian Rupees.
14. details json: Extended branch details and scheme metadata stored as JSON.
15. created at: Timestamp of repository indexing.


### 5. Asset Matches Table:

Contains candidate pairs generated by the automated matching algorithm.

1. id: String UUID primary key.
2. deceased person id: Foreign key to the verified deceased record.
3. financial asset id: Foreign key to the candidate financial asset.
4. matching score: Integer score between zero and one hundred.
5. matching reason: Semicolon separated breakdown of attributed points.
6. match category: Classification tier (Strong Potential Match, Requires Manual Review).
7. review status: Operational review state (Pending, Approved, Rejected).
8. created at: Timestamp of matching calculation.


### 6. Claimants Table:

Maintains profiles of individuals claiming inheritance or nominee rights.

1. id: String UUID primary key.
2. user id: Foreign key linking claimant to registered user.
3. deceased person id: Foreign key linking claimant to deceased family member.
4. name: Legal name of the claiming heir or nominee.
5. relationship to deceased: Declared relationship (Son, Daughter, Spouse, Legal Heir).
6. email: Official contact email.
7. mobile: Official contact mobile number.
8. claimant type: Capacity identifier (Nominee, Legal Heir).
9. status: Verification determination (Pending, Approved, Rejected).
10. admin notes: Institutional or administrative verification notes.
11. created at: Timestamp of claimant filing.


### 7. Claims Table:

Tracks the formal lifecycle of asset claims from filing through institutional determination.

1. id: String UUID primary key.
2. claim reference: Unique human readable tracking identifier like CLM 2026 88AB.
3. claimant id: Foreign key linking claim to verified claimant.
4. asset match id: Foreign key to the validated asset match.
5. deceased person id: Foreign key to the deceased record.
6. financial asset id: Foreign key to the targeted financial asset.
7. institution id: Foreign key to the reviewing financial institution.
8. status: Five stage lifecycle state (Submitted, Under Review, Documents Required, Approved, Completed).
9. remarks: Official remarks, documentation instructions or settlement notes.
10. submission date: Initial filing timestamp.
11. updated at: Most recent status transition timestamp.


### 8. Documents Table:

Stores metadata and storage paths for uploaded verification documents.

1. id: String UUID primary key.
2. user id: Foreign key to the uploading user.
3. deceased person id: Optional foreign key to associated deceased record.
4. claimant id: Optional foreign key to associated claimant.
5. claim id: Optional foreign key to associated claim.
6. document type: Classification (death certificate, identity proof, succession certificate).
7. file name: Original uploaded file name.
8. file path: Internal storage path on disk or cloud bucket.
9. file size: Integer file size in bytes.
10. content type: MIME type of the uploaded asset.
11. uploaded at: Upload timestamp.


### 9. Notifications Table:

Stores citizen alerts, matching discoveries and claim status updates.

1. id: String UUID primary key.
2. user id: Foreign key to recipient user.
3. title: Alert headline text.
4. message: Detailed explanatory content.
5. notification type: Event category (match found, claim update, system info).
6. is read: Boolean read indicator.
7. link: Optional deep link to relevant portal tab.
8. created at: Creation timestamp.


### 10. Audit Logs Table:

Maintains an immutable record of sensitive operational events.

1. id: String UUID primary key.
2. user id: Foreign key to acting user.
3. action: Action descriptor (USER LOGIN, MATCHING EXECUTED, CLAIM STATUS UPDATED).
4. entity type: Target domain entity (user, deceased person, claim, asset).
5. entity id: Primary key of target entity.
6. details: Comprehensive textual explanation of the action taken.
7. ip address: Client network IP address.
8. created at: Action timestamp.


## RESTful API Endpoints Reference:

The application exposes structured JSON endpoints organized across domain routers:

### Authentication Endpoints:

1. POST /api/auth/register: Registers new citizen account. Returns user profile and access token.
2. POST /api/auth/login: Authenticates existing credentials. Returns JSON Web Token and user profile.
3. GET /api/auth/me: Retrieves currently authenticated user session details.
4. POST /api/auth/demo login: Convenience endpoint for evaluators to switch roles rapidly.


### Deceased Records Endpoints:

1. POST /api/deceased: Submits new deceased person details and initiates civil queue.
2. GET /api/deceased: Retrieves authorized deceased records for current user or admin.
3. GET /api/deceased/{id}: Retrieves single deceased person profile by identifier.
4. PATCH /api/deceased/{id}/verify: Administrative endpoint approving death certificate and triggering auto matching.


### Asset Matching Endpoints:

1. POST /api/matching/{deceased id}: Executes the one hundred point matching engine for a verified deceased individual.
2. GET /api/matches/{deceased id}: Retrieves generated candidate matches with score breakdowns.


### Claim Tracking Endpoints:

1. POST /api/claimants: Registers claimant details and establishes legal relationship with deceased.
2. POST /api/claims: Initiates formal simulated claim on an identified asset match.
3. GET /api/claims: Retrieves claims filtered by user role and institutional assignment.
4. GET /api/claims/{id}: Retrieves single claim details including claimant and asset metadata.
5. PATCH /api/claims/{id}/status: Institutional desk endpoint updating claim status and appending nodal remarks.


### Document Storage Endpoints:

1. POST /api/documents/upload: Accepts multipart form data uploading death certificates and succession documents.
2. GET /api/documents/{id}/download: Serves authenticated document downloads with security checks.


### Administrative and Notification Endpoints:

1. GET /api/admin/stats: Delivers high level platform metrics across users, records and claims.
2. GET /api/admin/financial assets: Retrieves indexed repository records with optional search and category filters.
3. POST /api/admin/financial assets: Allows administrators to index new financial records into the database.
4. GET /api/admin/audit logs: Retrieves system audit logs in reverse chronological order.
5. GET /api/notifications: Retrieves alerts for the authenticated citizen or officer.
6. PATCH /api/notifications/{id}/read: Marks a single notification as read.
7. POST /api/notifications/mark all read: Marks all notifications as read for current user.


## Security and Authorization Architecture:

1. Cryptographic Hashing: Passwords are encrypted using the bcrypt algorithm with salt rounds managed by passlib.
2. JSON Web Token Protection: Bearer tokens are signed using HMAC SHA256 and verified on every protected API call.
3. Role Based Access Middleware: Role guards ensure family users cannot access administrative commands or review claims from other citizens.
4. Institutional Data Partitioning: Institution representatives can view and update only claims matching their assigned institution identifier.
5. Supabase Row Level Security: Cloud PostgreSQL policies guarantee database level isolation even if application endpoints are bypassed.


## Web Cybersecurity Defenses and Threat Mitigations:

The Virasat Setu platform incorporates multi tiered defensive cybersecurity controls designed to eliminate standard Open Web Application Security Project vulnerability vectors:

### 1. SQL Injection Defense in Depth:
1. Primary Defense: SQLAlchemy Object Relational Mapping automatically implements parameterized queries with separated query compilation and bound values, preventing SQL syntax manipulation.
2. Secondary Signature Filter: The validation engine screens incoming textual fields with regular expressions detecting common injection signatures like UNION SELECT, OR 1=1, DROP TABLE, DELETE FROM and comment dashes.
3. Search Query Sanitization: Administrative search endpoints enforce input length boundaries and execute safe parameterized string filters.

### 2. Cross Site Scripting (XSS) Mitigation:
1. Backend Entity Encoding: The text sanitizer strips null bytes and control characters while replacing sensitive characters like ampersands and angle brackets with secure HTML entities.
2. Script Pattern Blocking: Pydantic field validators inspect submitted payloads and reject script tags, javascript URI schemes, event handler attributes and iframes with HTTP 400 Bad Request.
3. Frontend Template Escaping: All dynamic document template literals in the client application invoke an escapeHTML utility before setting innerHTML properties, ensuring untrusted user content cannot execute as markup.

### 3. Cross Site Request Forgery (CSRF) Protection:
1. Bearer Token Isolation: The platform stores session JSON Web Tokens in browser local storage and transmits them via Authorization headers. Browsers never attach Authorization headers to cross origin requests automatically.
2. Custom Verification Headers: The CSRF Protection Middleware requires state modifying requests (POST, PUT, PATCH, DELETE) to present custom client headers like X Requested With or X CSRF Token, which cross site forms cannot forge.
3. Preflight Enforcement: Custom headers force modern browsers to execute Cross Origin Resource Sharing preflight OPTIONS requests, blocking unauthorized cross origin submission attempts.

### 4. HTTP Defensive Security Headers:
The platform attaches comprehensive security headers to all HTTP responses:
1. Content Security Policy: Enforces default self origin restrictions while whitelisting designated trustworthy content delivery networks.
2. X Frame Options: Set to DENY to prevent Clickjacking attacks and disallow embedding the application inside foreign iframes.
3. X Content Type Options: Set to nosniff to prevent browsers from executing files with mismatched MIME types.
4. X XSS Protection: Set to 1 mode=block for defense on legacy browser agents.
5. Referrer Policy: Configured as strict origin when cross origin to eliminate sensitive query leakage.
6. Permissions Policy: Restricts unneeded hardware APIs including camera, microphone and geolocation.
7. Cross Origin Opener Policy: Set to same origin to isolate the browsing context.

### 5. Document Storage and Path Traversal Hardening:
1. Extension Whitelisting: Document upload endpoints strictly accept only verified extensions including .pdf, .png, .jpg, .jpeg and .webp.
2. File Size Enforcement: Maximum file size is strictly capped at ten megabytes to prevent server storage exhaustion.
3. Path Traversal Elimination: Filenames containing path traversal tokens like double periods or directory slashes are detected and blocked immediately.
4. Random UUID Storage: Uploaded files are persisted using randomly generated UUIDs, completely detaching physical filenames on disk from user supplied names.
5. Insecure Direct Object Reference (IDOR) Protection: Document download endpoints authenticate the requesting user and verify ownership, restricting downloads strictly to the document owner, authorized administrators or assigned institutional representatives.

### 6. Brute Force and Abuse Rate Limiting:
1. In Memory Sliding Window: A sliding window rate limiting middleware tracks incoming client IP requests across rolling sixty second intervals.
2. Authentication Route Protection: Login and registration endpoints are protected with a strict rate threshold of thirty requests per minute per IP address to thwart credential stuffing.
3. General API Rate Limiting: Standard platform endpoints are governed by a three hundred request per minute ceiling, guarding against denial of service and automated scraping.


## Artificial Intelligence and Machine Learning Architecture:

The Virasat Setu platform integrates lightweight, highly efficient machine learning and artificial intelligence capabilities engineered for instant execution within serverless environments:

### 1. Virasat AI Legal Copilot Architecture:
1. Dual Engine Framework: The AI Copilot operates a resilient dual layer architecture combining external Google Gemini generative intelligence with an embedded, zero latency Indian Succession Legal Knowledge Engine.
2. Generative Processing: Generative queries utilize the Gemini 3.8 Flash model via secure API endpoints, synthesizing citizen legal inquiries regarding inheritance and claims.
3. High Availability Fallback: If external connectivity is delayed beyond two seconds or unavailable, the system automatically falls back to an offline rule based inference engine.
4. Comprehensive Succession Coverage: The offline legal knowledge base encodes statutes including the Hindu Succession Act 1956, Indian Succession Act 1925, banking deceased claim regulations, nominee versus legal heir legal rights, and documentation mandates across institutions.
5. Strict Endpoint Gating: The copilot endpoint enforces authentication rate limiting and sanitizes all incoming inquiry text against prompt injection attempts.

### 2. Machine Learning Indian Name Transliteration Engine:
1. Cross Script Phonetic Normalization: Indian civil records exhibit frequent phonetic variations in English transliteration across regional municipal offices.
2. Phonetic Transformation Rules: The engine applies linguistic transformations mapping regional consonant combinations, collapsing aspirates, normalizing long vowel digraphs, and reducing repetitive consonant clusters.
3. Character N Gram Jaccard Similarity: To capture subtle spelling deviations without external heavy transformer models, the system computes character bigram Jaccard similarity between applicant names and institutional ledger entries.
4. Composite Transliteration Scoring: Name matching integrates exact token matching, initial sequencing, phonetic Metaphone representation, and character bigram intersection, providing high accuracy matching across diverse Indian regional variants like Laxmi versus Lakshmi and Agarwal versus Aggarwal.

### 3. Claim Health and Approval Probability Predictor:
1. Citizen Prescriptive Intelligence: When preparing an asset claim, citizens receive a real time evaluation of claim readiness and approval probability scored between twenty five and ninety eight percent.
2. Multi Factor Readiness Assessment: The prediction algorithm evaluates five core dimensions including claimant relationship capacity, legal heir standing, match score confidence, documentation completeness, and asset dormancy tenure.
3. Prescriptive Guidance: The model produces actionable steps highlighting required affidavits, succession certificates, or indemnity bonds needed to maximize approval likelihood prior to formal submission.

### 4. AI Fraud and Anomaly Detection Center:
1. Role Based Anomaly Screening: To protect citizen privacy and institutional integrity, fraud detection analytics are strictly isolated and accessible only to verified administrators and institutional desk officers.
2. Duplicate Claim Contention Detection: The anomaly engine flags conflicting claims filed by multiple distinct applicants targeting the same underlying financial asset.
3. High Value Dormancy Verification: Unclaimed assets exceeding five lakh rupees with dormant tenure over ten years are flagged for mandatory enhanced verification and municipal cross check.
4. Relationship Capacity Anomaly Scoring: Flags applications where declared claimant relationship exhibits inconsistencies with known nominee declarations or succession hierarchy.


## Google OAuth 2.0 Authentication Integration:

The platform supports secure single sign on using the Google OAuth 2.0 authorization framework:

1. Protocol Conformance: Implements the OpenID Connect and OAuth 2.0 authorization code flow compliant with RFC 6749.
2. Credential Verification: Client tokens are validated against Google token verification services, extracting verified email addresses and user names.
3. Automatic Provisioning: First time Google authenticated users are automatically provisioned as citizen family users in the database with secure cryptographic password hashes.
4. Session Token Minting: Upon successful verification, the platform issues an internal JSON Web Token authorizing subsequent API transactions with standard role based access controls.
